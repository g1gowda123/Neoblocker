## 2024-06-13 - Extension Background Script Error Information Leakage and Lack of Validation
**Vulnerability:** The extension `background.ts` handler was exposing internal exception details (`String(err)`) to content scripts across the extension message passing boundary, potentially leading to information disclosure. Further, parameters such as `videoId` and `text` were not validated or bounds-checked, allowing for arbitrary inputs (length unbounded or arbitrary strings) that could lead to DoS, memory exhaustion, SSRF or request smuggling down the line.
**Learning:** Browser extension message passing must be treated as crossing a security boundary. Inputs received from content scripts running in the context of potentially hostile web pages must be strictly validated. Errors propagated back over message passing should be generic to prevent leaking stack traces or internal implementation details.
**Prevention:** Always validate and bound inputs in background service workers using explicit typing, regex validation, and length constraints. Return generic, safe error messages to content scripts to prevent internal information leakage.

## 2024-06-28 - Log Injection Fix in Verification API
**Vulnerability:** User-controlled input (`source_url`) and external data (`response.text`) were being printed directly to stdout using `print()` without sanitization. This allowed attackers to inject fake log entries by including newline (`\n`) or carriage return (`\r`) characters in the input.
**Learning:** Standard print statements and standard Python `logging` do not automatically escape newlines in log messages. When user input containing newlines is logged, it can create forged log entries that confuse administrators or mask malicious activity (CWE-117).
**Prevention:** Always use a properly configured logging framework instead of raw `print` statements, and explicitly sanitize any user-controlled or external strings by replacing `\n` and `\r` with their escaped representations (`\\n` and `\\r`) before logging them.

## 2024-05-27 - [Async SSRF Protection]
**Vulnerability:** Blocking synchronous DNS lookup (`socket.gethostbyname`) inside an asynchronous FastAPI endpoint, potentially causing the event loop to block. Insufficient IP checks for SSRF protection.
**Learning:** In asynchronous Python apps, using synchronous functions like `socket.gethostbyname()` can block the event loop and degrade performance. `asyncio.get_running_loop().getaddrinfo()` must be used instead. Additionally, when mitigating SSRF, all possible resolved IPs from `getaddrinfo` must be checked, and filters should include `is_multicast` and `is_unspecified` (0.0.0.0 or ::) alongside private/loopback/link-local ranges.
**Prevention:** Always use non-blocking functions for DNS resolution in async code. Iterate through all resolved IPs and use `ipaddress` to strictly block private, loopback, link-local, multicast, and unspecified addresses.

## 2024-06-29 - [TOCTOU DNS Rebinding SSRF Fix in Chromium Crawler]
**Vulnerability:** The FastAPI verification endpoint mitigated SSRF by checking `getaddrinfo` on the provided hostname and blocking private/loopback IPs. However, it then passed the original URL to `AsyncWebCrawler` (a playwright/chromium wrapper). This creates a Time-of-Check to Time-of-Use (TOCTOU) DNS rebinding vulnerability, as Chromium performs its own DNS resolution, allowing an attacker to rapidly change the DNS record to point to an internal IP after the check passed but before the crawl occurs.
**Learning:** Simply replacing the hostname with the raw IP address in an HTTPS URL (e.g., `https://1.1.1.1/`) breaks Server Name Indication (SNI) during the TLS handshake, causing the crawl to fail on almost all modern websites, even if the `Host` HTTP header is injected.
**Prevention:** To mitigate DNS rebinding in Chromium-based libraries without breaking SNI, use the `--host-resolver-rules=MAP <hostname> <validated_ip>` command-line flag (e.g., via `BrowserConfig`'s `extra_args` in `crawl4ai`). This forces the browser to use the safely validated IP address at the network layer while preserving the original hostname for the TLS SNI and HTTP Host headers.

## 2024-06-30 - Argument Injection Vulnerability via BrowserConfig CLI Args
**Vulnerability:** The FastAPI endpoint extracted `parsed_url.hostname` from user input and directly injected it into the `--host-resolver-rules` command-line template for Chromium (via `BrowserConfig`). Without strict validation, a maliciously crafted hostname containing spaces or other shell metacharacters could allow an attacker to inject arbitrary command-line arguments into the headless browser process.
**Learning:** Even when inputs are technically parsed correctly by URL parsers (which often tolerate a wide array of characters), passing those extracted values into command-line templates or shell executions creates an argument/command injection risk.
**Prevention:** Always apply strict regex validation (e.g., `r"^([a-zA-Z0-9.-]+|\[[a-fA-F0-9:]+\])$"`) to extract safe, expected values before interpolating user-controlled strings into command-line arguments or template strings used for process execution.

## 2024-07-04 - Denial of Service (DoS) via Unbounded Input Text
**Vulnerability:** The API endpoint `/verify` accepts a `text` parameter in the `VerifyRequest` Pydantic model without any length constraint. This lack of bounding allows an attacker to send an arbitrarily large string, which could lead to severe memory exhaustion or cause the underlying LLM processing (Google GenAI) to incur excessive compute overhead or token limits.
**Learning:** Even if the input is safely passed to downstream APIs, failing to enforce length bounds on user-provided strings leaves the service vulnerable to Application-Layer DoS attacks.
**Prevention:** Always enforce explicit input length validation directly on request payloads using validation frameworks (e.g., Pydantic's `Field(max_length=X)`) before the input reaches any computationally expensive logic or external APIs.

## 2024-08-01 - SSRF and Argument Injection bypass via IPv6 parsing
**Vulnerability:** The argument injection regex strictly required IPv6 brackets `\[...\]` for the parsed hostname. However, Python's `urlparse.hostname` automatically strips brackets from IPv6 URLs (e.g., `http://[::1]/` becomes `::1`). This mismatch blocked valid IPv6 requests. Furthermore, checking only `is_private`/`is_loopback` was insufficient for preventing SSRF against reserved, globally non-routable IP ranges (like `100.64.0.0/10` or `240.0.0.0/4`).
**Learning:** When writing regexes based on url parser outputs, you must consider the internal normalization done by the parser (e.g. bracket stripping). When mitigating SSRF via an allowed public URL proxy, `ip.is_global` provides a more robust and stricter guard against internal/special-purpose networks than a blocklist of `is_private` and `is_loopback`.
**Prevention:** Test hostname regex validation directly against the `urlparse` output rather than raw strings. Ensure SSRF checks explicitly require IP addresses to be globally routable (`ip.is_global`), acting as an allowlist instead of relying solely on a blocklist of private IPs.

## 2024-08-15 - [Application-Layer DoS via Unbounded URL]
**Vulnerability:** The API endpoint `/verify` accepts a `source_url` parameter in the `VerifyRequest` Pydantic model without any length constraint. This allowed an attacker to send an arbitrarily large string as the URL, potentially leading to memory exhaustion or excess CPU usage during regex validation and Chromium processing.

**Prevention:** Always enforce explicit input length limits on all user-provided strings (e.g., `Field(max_length=2048)`) before passing them to internal processing logic.

## 2024-08-30 - [IPv6 TOCTOU Bypass in Chromium Crawler]
**Vulnerability:** The FastAPI verification endpoint resolved the hostname to an IP address to prevent DNS rebinding attacks (TOCTOU). However, if the resolved IP was an IPv6 address, it was passed directly to Chromium's `--host-resolver-rules=MAP <hostname> <ip>` argument without brackets. Chromium silently rejected the malformed MAP rule (it expects IPv6 addresses to be enclosed in brackets, e.g. `[::1]`) and fell back to resolving the hostname itself, reinstating the TOCTOU DNS rebinding vulnerability for IPv6 addresses.
**Learning:** Tools relying on IP arguments might require specific formatting for IPv6 addresses (like brackets) that differ from the raw IP string returned by standard DNS resolution libraries. If these tools fail open (i.e. silently ignore the malformed rule and proceed with default behavior), security controls can be bypassed.
**Prevention:** When passing IPv6 addresses as arguments or in templates to other tools, always ensure they are correctly formatted (e.g. enclosed in `[]` for Chromium/URIs) by checking the IP version (`ip_obj.version == 6`) and transforming the string accordingly.

## 2024-09-15 - [Log Injection Vector via Exception Objects]
**Vulnerability:** Even when user input properties are explicitly sanitized before logging, catching and logging the raw exception object (`e`) without sanitization re-introduces a Log Injection vulnerability. Framework exceptions (like `JSONDecodeError` or network errors) can inherently contain the unsanitized input that triggered them (e.g., the raw payload or URL).
**Learning:** Exception messages must be treated as untrusted data if the exception was generated by processing user-controlled input. Passing `e` into an f-string implicitly calls `str(e)`, embedding potentially malicious newlines into the log format.
**Prevention:** Always cast exceptions to strings and explicitly apply logging sanitization functions (e.g., `sanitize_log(str(e))`) before incorporating them into security or operational logs.

## 2025-02-28 - [SSRF via Untrusted URL from Parsed HTML]
**Vulnerability:** In `src/background.ts`, the extension fetched subtitles by sending a GET request to `englishTrack.baseUrl`. However, this URL was extracted from a JSON object (`ytInitialPlayerResponse`) that was parsed from the page's HTML using a loose regex. An attacker could inject a fake JSON block into the video metadata (such as the title or description tag), hijacking the parsed URL and causing the background script to send arbitrary GET requests (SSRF) to internal or malicious endpoints.
**Learning:** URLs extracted dynamically from DOM or parsed HTML should be treated as untrusted user input, even if they nominally represent first-party data. Background scripts bypass CORS and can reach sensitive internal endpoints, making SSRF highly dangerous.
**Prevention:** Always strictly validate and parse URLs extracted from web content before passing them to `fetch()`. Enforce allowed schemes (HTTPS) and allowed hostnames (e.g., `*.youtube.com`, `*.googlevideo.com`) to prevent attackers from forcing the application to retrieve arbitrary resources.

## 2024-10-30 - [Regex Anchor Vulnerability in Argument Injection Filter]
**Vulnerability:** The Python regex used to validate hostnames (`r"^([a-zA-Z0-9.-]+|[a-fA-F0-9:]+)$"`) used the `$` anchor. In Python, `$` matches the end of the string OR just before a newline character at the end of the string. This allowed a malicious hostname ending with a newline (e.g. `example.com\n`) to pass the regex check, opening up potential newline or argument injection vulnerabilities downstream when the hostname was passed into CLI arguments or templates.
**Learning:** Python's `$` regex anchor behaves differently from what is often expected, allowing a trailing newline to sneak past strict format checks.
**Prevention:** When enforcing strict regex patterns on untrusted input to prevent argument or newline injection, always use the `\Z` anchor instead of `$`. The `\Z` anchor guarantees the match only happens at the absolute end of the string, preventing any trailing newline bypasses.

## 2024-11-20 - [Weak PRNG for DOM Component Identifiers]
**Vulnerability:** The code utilized `Math.random().toString(36).substring(7)` repeatedly in `src/contents/content-observer.tsx` to generate what were intended to be unique tracking identifiers for DOM elements (`videoId`, `commentId`, and React keys).
**Learning:** `Math.random()` is not a cryptographically secure pseudo-random number generator (CSPRNG). While generating DOM element IDs is not typically a critical cryptographic operation (unlike generating session tokens or salts), using weak RNGs creates an unnecessary risk of ID collisions, especially in high-volume, long-lived pages like YouTube where elements are repeatedly created and destroyed. It's a common static analysis finding and a bad habit that can accidentally leak into sensitive contexts.
**Prevention:** Always use the built-in, cryptographically secure `crypto.randomUUID()` when generating universally unique identifiers in modern web environments, even for non-security-critical component tracking.
